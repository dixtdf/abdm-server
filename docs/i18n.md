# Internationalisation (i18n)

The UI ships two locales today: `en-US` (the fallback and source of truth) and
`zh-CN`. Locale files live in `web/src/locales/<locale>.json` and are consumed
by `vue-i18n`.

## Key naming rules

Keys are hierarchical and lowercase, with dot-separated segments. The first
segment is the domain, and the last segment is either a stable machine code or
a camelCase field name.

| Prefix | Contains | Example |
| --- | --- | --- |
| `common.*` | shared vocabulary reused across screens | `common.cancel`, `common.retry`, `common.loading` |
| `nav.*` | navigation / route labels | `nav.downloads`, `nav.history`, `nav.settings` |
| `download.*` | task list, task actions, task fields | `download.add`, `download.pauseAll`, `download.field.speed` |
| `download.status.*` | one key per `DownloadState` | `download.status.DOWNLOADING`, `download.status.COMPLETED` |
| `errors.<CODE>` | one key per error code from `docs/api.md` | `errors.PATH_OUTSIDE_DOWNLOAD_ROOT` |
| `settings.*` | settings form | `settings.defaultConnections`, `settings.authMode` |
| `units.*` | units and suffixes | `units.perSecond`, `units.remaining` |
| `history.*` | history screen | `history.outcome.COMPLETED` |

Rules:

1. **`download.status.*` mirrors the enum exactly.** The backend sends
   `state: "DOWNLOADING"`; the frontend renders `download.status.DOWNLOADING`.
   Never translate the state string itself.
2. **`errors.<CODE>` mirrors `docs/api.md` exactly**, uppercase code, no
   translation of the code. The backend never sends a localized sentence: it
   sends `{ "error": { "code": "...", "params": {...} } }` and the frontend
   renders `errors.<CODE>` with `params` interpolated.
3. **One key, one meaning.** Do not reuse `common.cancel` for a destructive
   "delete" action; add `common.delete`.
4. **Stable keys over readable keys.** Renaming a key means touching every
   locale file; extend instead (`download.action.removeFile`).
5. **No sentence building in code.** Concatenating fragments produces
   untranslatable text — put the whole sentence in a key and use placeholders.
6. **JSON only.** No JS/TS locale modules, so the files stay diffable and a
   translation platform can consume them directly.

## Placeholders

- Named placeholders only: `"download.eta": "剩余 {duration}"`, never
  positional `%s`. The gate recognises `{name}` with letters, digits and
  underscores; anything else is invisible to it.
- Interpolation is done by vue-i18n at render time: `t('errors.CHECKSUM_MISMATCH', { expected, actual })`.
- A placeholder must exist in every locale file; a missing one renders the raw
  `{name}` and is caught in review.
- Placeholders carry no formatting themselves. Format with `Intl`
  (see below) and pass the resulting string in.
- Countable strings use vue-i18n pluralisation (`"download.count": "无任务 | {n} 个任务"`),
  never a hand-written `if (n === 1)`.

## Adding a locale

1. Create `web/src/locales/<locale>.json` as a copy of `en-US.json` — never as a
   partial file, because the CI gate compares key sets.
2. Translate the values. Do not translate keys, `errors.<CODE>` codes or
   placeholder names.
3. Register the locale in the frontend i18n setup (`web/src/i18n.ts`) — import,
   `messages` map, and a display-name entry for the language switcher.
4. Run the gate locally:

   ```bash
   cd web
   npm run i18n:check
   ```

5. Switch the UI language once and walk the task list, the history table and one
   forced error (e.g. delete a file outside the root) to confirm interpolation.

## The CI gate

`scripts/check-i18n.mjs`, run by `npm run i18n:check`, enforces:

- every locale file under `web/src/locales` parses as JSON;
- every value is a non-empty string;
- every key present in `en-US` exists in the other locales;
- every error code listed in `docs/api.md` has an `errors.<CODE>` key in **every**
  locale, and conversely every `errors.*` key exists in that catalogue;
- no extra keys that `en-US` does not have (typo protection);
- identical `{placeholder}` sets per key across locales.

The script exports `checkI18n`, `parseErrorCodes`, `flatten` and `placeholders`,
so the same checks can be driven from vitest with a fixture directory instead of
being duplicated in the test suite.

The gate runs in the frontend CI job, in the release workflow, and inside the
Docker `web` stage (`npm run i18n:check && npm run build`), so a missing
translation cannot reach a published image.

## Dates, numbers and units

Never format numbers by string concatenation and never hard-code a date pattern.
Use `Intl` with the active locale:

| Value | API | Notes |
| --- | --- | --- |
| Byte sizes | `Intl.NumberFormat(locale, { style: 'unit', unit: 'megabyte', maximumFractionDigits: 2 })` | pick the unit from the byte count first |
| Speeds | size formatter + `units.perSecond` | `t('units.perSecond')` supplies e.g. `/s` or `/秒` |
| Percentages | `Intl.NumberFormat(locale, { style: 'percent', maximumFractionDigits: 1 })` | progress comes as `0..1` |
| Dates/times | `Intl.DateTimeFormat(locale, ...)` | epoch milliseconds from the API |
| Durations | format seconds in a helper, then a `units.*` suffix | `etaSeconds == -1` means unknown → `common.unknown` |

Timestamps are UTC epoch milliseconds on the wire; the server never sends a
pre-formatted date string.

## Fallback behaviour

- `fallbackLocale: 'en-US'`. A missing key in `zh-CN` renders the `en-US` text
  rather than the raw key path.
- The gate makes that situation a build failure, so the fallback exists for
  safety, not as a translation strategy.
- If the stored `ui.locale` is unknown (browser locale we do not ship), the app
  falls back to `en-US` and rewrites `localStorage`.
- `ui.locale` and `ui.theme` are browser preferences (`localStorage`), not
  server settings — a server never forces a locale.

## Future: Crowdin / Weblate

The locale files are deliberately plain flat-path JSON with stable keys and
named placeholders, which is exactly the shape translation platforms expect:

- **Crowdin** — point a project at `web/src/locales/*.json` using "JSON (nested)"
  with keys as identifiers; configure `en-US.json` as the source file and let it
  open pull requests that the existing `npm run i18n:check` gate validates.
- **Weblate** — add a "JSON file" component with a file mask of
  `web/src/locales/*.json` and a base file of `en-US.json`.

Either way the workflow is the same: the platform only ever edits locale JSON,
CI re-runs the gate, and nothing else in the repository needs to change. The
error-code catalogue in `docs/api.md` remains the contract that tells
translators which `errors.<CODE>` keys must exist.
